DAY 02

VPC & Multi-AZ Network

COMPLETED

Provisioned the AWS network foundation with Terraform across two Availability Zones.

VPC CIDR

10.0.0.0/16 VPC providing isolated network boundaries and sufficient address space across availability zones.

Application Subnets

10.0.1.0/24 in us-east-1a and 10.0.2.0/24 in us-east-1b associated with the public route table.

Database Subnets

10.0.11.0/24 in us-east-1a and 10.0.12.0/24 in us-east-1b reserved strictly for future RDS private database workloads.

Routing & Gateways

Internet Gateway attached with default route (0.0.0.0/0 -> igw) on the public route table. Database route table contains local VPC route only.

Subnet Separation Rationale

Application and database subnets are separated to enforce network isolation. Database subnets have no internet gateway route, guaranteeing that database instances cannot be directly addressed or scanned from the public internet.

DAY 03

EC2 & Security Groups

⚠ INCIDENT #001 COMPLETED

Deployed EC2 compute and implemented controlled HTTP and SSH access.

Compute Deployment

An EC2 instance was deployed into the application subnet and verified as running with public IPv4 addressing.

Security Group Design

HTTP TCP/80 is publicly reachable for application web traffic. SSH TCP/22 is restricted exclusively to the administrator IP.

INCIDENT Incident #001 — EC2 SSH Authentication Failure

Initial SSH connection attempt failed with 'Permission denied (publickey)'. Terraform state inspection showed key_name was omitted (key_name = null).

ROOT CAUSE Root Cause & Remediation

The EC2 instance was provisioned without an EC2 key pair. Updated Terraform compute module with key_name = var.key_name, restoring secure SSH access.

Engineering Lesson

Always declare authentication credentials explicitly in IaC; verify access immediately upon initial deployment before proceeding to software provisioning.

DAY 05

Application Load Balancer

COMPLETED

Introduced an Application Load Balancer across multi-AZ public subnets with target group health checks and security group tiering.

Multi-AZ ALB Provisioning

Deployed an internet-facing Application Load Balancer spanning public subnets in us-east-1a and us-east-1b via Terraform.

Target Group & Health Check

Configured HTTP/80 target group checking /health endpoint with 200 OK contract (30s interval, 5s timeout, 2 healthy / 2 unhealthy thresholds).

Security Group Tiering

ALB security group allows HTTP/80 from 0.0.0.0/0. EC2 security group allows TCP/80 exclusively from the ALB security group.

Traffic Tiering Rationale

Restricting EC2 ingress exclusively to the ALB security group ensures all client traffic passes through the ALB for inspection and load balancing, protecting EC2 nodes from direct internet exposure.

End-to-End Verification

Confirmed HTTP 200 responses for /health, /ready, and portfolio UI via ALB DNS name across both availability zones.

INCIDENT REPORT PRODUCTION INVESTIGATION & RECOVERY
DAY 03 INCIDENT #001 LOW ACCESS / COMPUTE

EC2 SSH Authentication Failure

Symptom

ssh ubuntu@<host>

Permission denied (publickey)

Investigation

  • EC2 instance was verified in running state in application subnet
  • Security group allowed inbound TCP/22 from administrator IP
  • Public IPv4 address was attached and responding to network probes
  • Terraform state inspection showed key_name = null
ROOT CAUSE

The EC2 instance was provisioned without an EC2 key pair because the key_name parameter was omitted in the Terraform compute configuration.

Remediation

key_name = var.key_name

Updated the Terraform configuration to explicitly associate the instance with the authorized SSH key pair. Applied changes and confirmed immediate successful authentication.

Validation & Engineering Lesson

Validated SSH connection via key pair. Established a core engineering guideline: all compute definitions in IaC must enforce explicit key pair assignment before initiating software provisioning.

DAY 06 INCIDENT #002 HIGH AUTO SCALING / RECOVERY TEST

Instance Replacement Test (Controlled Termination)

Scenario

An active application EC2 instance in us-east-1a was deliberately terminated via AWS CLI to test Auto Scaling Group self-healing and zero-downtime recovery.

Expected Behavior

The Auto Scaling Group detects capacity loss via ELB health check, terminates the degraded node, provisions a replacement instance from the Launch Template, and registers it to the Target Group.

OBSERVED BEHAVIOR 
Instance Terminated (us-east-1a)
       ↓
ASG detected capacity deficit (1/2 desired)
       ↓
Scaling activity initiated replacement launch
       ↓
Cloud-init executed user-data bootstrap
       ↓
Target registered to ALB Target Group
       ↓
Health checks passed HTTP 200 OK (2/2 capacity restored)

Validation

Target Group reached full healthy state (2/2 instances) within evaluation threshold. Public ALB endpoint maintained 100% uptime with zero client 5xx errors during node replacement.

Engineering Lesson

Stateless compute paired with immutable Launch Templates and health-aware Auto Scaling Groups ensures automated self-healing without requiring human intervention during infrastructure failures.

TECHNOLOGY DECISIONS WHY THESE COMPONENTS?
NETWORK ISOLATION

VPC & Subnet Design

Provides private network boundaries with explicit tiering. Public application subnets receive ingress from the load balancer, while private database subnets have no internet gateway route, guaranteeing databases are unreachable from the public internet.

TRAFFIC DISTRIBUTION

Application Load Balancer

Distributes Layer 7 HTTP traffic evenly across multiple Availability Zones. Continuously probes backend nodes against the /health contract, automatically routing requests away from degraded instances.

DEFENSE IN DEPTH

Security Groups

Enforces least-privilege traffic flow through security group referencing. The ALB allows public HTTP/80, while EC2 security groups permit HTTP ingress exclusively from the ALB security group ID.

IMMUTABLE COMPUTE

Launch Template

Codifies instance configuration, dynamic Ubuntu LTS AMI resolution via data.aws_ami, instance sizing, and automated cloud-init bootstrap, ensuring all compute capacity is created consistently.

SELF-HEALING ARCHITECTURE

Auto Scaling Group

Maintains desired compute capacity across two Availability Zones. Integrated with ELB health checks to automatically terminate degraded instances and launch healthy replacements without manual intervention.

RUNTIME ISOLATION

Node Version Manager (NVM)

Installs and manages Node.js LTS in non-root user space (/home/ubuntu/.nvm), preventing system package pollution and ensuring predictable, isolated application runtimes across deployments.

WEB TIER

Nginx Reverse Proxy

Acts as a high-performance reverse proxy listening on port 80 and forwarding requests to the Node.js application process on port 3000, managing header sanitization, connection buffering, and host routing.
