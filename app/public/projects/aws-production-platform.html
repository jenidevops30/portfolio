TECHNOLOGY DECISIONS
TECHNOLOGY DECISION

Why a Launch Template?

Individual EC2 instances are difficult to reproduce consistently. A Launch Template defines the expected instance configuration so new application capacity can be created consistently.

DESIGN DECISION

Why Multi-AZ?

Application capacity is distributed across two Availability Zones so that the platform does not depend on a single Availability Zone.

Cloudflare

Used as the edge ingress layer for authoritative DNS, edge SSL termination, proxying, and distributed denial-of-service (DDoS) mitigation.

Application Load Balancer

Provides Layer 7 HTTP/HTTPS traffic distribution across multi-AZ public subnets with continuous target health checking against the /health contract.

Auto Scaling Group

Ensures high availability and automated replacement of unhealthy compute instances across multiple availability zones.

RDS MariaDB

Isolates the persistent database tier in private subnets, completely disconnected from direct internet access, with automated backups and failover standby.

AMI MANAGEMENT

The Launch Template uses Terraform's AWS AMI data source to identify the latest matching Ubuntu 24.04 LTS image rather than hardcoding a single AMI ID. 

data "aws_ami" "ubuntu" {
  most_recent = true

  owners = ["099720109477"]

    name = "architecture"
    values = ["x86_64"]
  }
}

INCIDENT REPORT
INCIDENT #001 LOW ACCESS / COMPUTE

EC2 SSH Authentication Failure

Symptom

ssh ubuntu@<public-ip>

Permission denied (publickey)

Investigation

  • EC2 was running
  • Public IP was assigned
  • Application subnet was correct
  • TCP/22 was allowed from administrator IP
  • Terraform showed key_name = null
ROOT CAUSE

The EC2 instance was provisioned without an EC2 key pair, preventing SSH authentication.

Remediation

key_name = var.key_name

The Terraform configuration was updated to explicitly associate the EC2 instance with the AWS key pair.

INCIDENT #002 MEDIUM ROUTING / WEB TIER / APPLICATION

Nginx Reverse Proxy 404 / Missing Upstream

Symptom

$ curl -i http://54.236.188.6/health

HTTP/1.1 404 Not Found
Server: nginx/1.24.0 (Ubuntu)

Investigation

  • Security group allowed TCP/80 ingress
  • Nginx service was active (running) on EC2
  • Nginx served static files from /var/www/html with try_files $uri $uri/ =404
  • Node.js app running on loopback: curl http://localhost:3000/health -> 200 OK
  • Inbound port 80 traffic was not forwarded to Node process on port 3000
ROOT CAUSE

Nginx was installed with default distribution configuration serving static files from /var/www/html. No reverse proxy directive (proxy_pass) was configured to bridge incoming public requests on port 80 to the Node.js application process on port 3000.

Remediation

location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

Configured reverse proxy upstream in Nginx, validated syntax with sudo nginx -t, reloaded Nginx, and deployed the Node.js application as a persistent systemd service (portfolio.service). Validated curl -i http://54.236.188.6/health -> 200 OK.

INCIDENT #003 HIGH LOAD BALANCING / SECURITY GROUP / NETWORK TIERING

ALB 502 Bad Gateway / Unhealthy Target Group

Symptom

$ curl -i http://devops-portfolio-lab-alb-891893207.us-east-1.elb.amazonaws.com/health

HTTP/1.1 502 Bad Gateway
Server: awselb/2.0
Content-Length: 0

Investigation

  • ALB provisioned in public subnets across us-east-1a and us-east-1b
  • Direct curl to EC2 instance on port 80 succeeded: 200 OK
  • Target Group showed target status: unhealthy (Health checks failed)
  • ALB access logs confirmed 502 responses to clients
  • EC2 security group allowed ingress only from administrator IP, missing rule for ALB security group
ROOT CAUSE

The EC2 security group did not permit inbound HTTP traffic from the ALB security group (sg-01458968cdedf7043). ALB health check probes on port 80 were dropped by the EC2 firewall, preventing the load balancer from establishing a TCP handshake with backend instances.

Remediation

resource "aws_security_group_rule" "ec2_from_alb" {
  type                     = "ingress"
  from_port                = 80
  to_port                  = 80
  protocol                 = "tcp"
  source_security_group_id = aws_security_group.alb.id
  security_group_id        = var.ec2_security_group_id
}

Implemented security group tiering in Terraform by adding an explicit ingress rule allowing TCP/80 exclusively from the ALB security group. Once applied, targets transitioned to healthy within two evaluation cycles, and the ALB returned 200 OK on all routes.
